# Verified Archive Transaction Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a desktop user review exact discovered files, choose the single authoritative Vault, approve an immutable plan, and copy originals into that Vault only after independent SHA-256 verification and durable registration.

**Architecture:** Discovery produces expiring opaque proposal and item identifiers plus SHA-256 identities, while a private Rust registry retains the exact reviewed paths. A Rust-owned native directory picker establishes one in-memory Vault authority. Archive plans bind the proposal, selected items, current Vault authority, exact identities, resolved destination paths, expiry, and a single-use nonce; the trusted core reopens and re-hashes sources before a staged copy, verifies staged bytes independently, persists operation and registration records inside the Vault, atomically exposes the destination, and preserves every source.

**Tech Stack:** Tauri 2, Rust, `cap-std`, `sha2`, `tauri-plugin-dialog`, Serde JSON, React, TypeScript, Vitest, Testing Library, Playwright.

---

## Scope boundary

This plan implements one safe archive intake path. It deliberately excludes
classification, canonical renaming, source cleanup, undo, profile import,
knowledge generation, graph persistence, and MCP transports. Intake
destinations use `Originals/<sha256>/<original-name>` until a later approved
classification plan proposes a category path.

3. unreadable staged output causes visible failure and no registration;

6. exposure before final registration reconciles to either fully verified
   committed state or no target and no registration;
7. every terminal result records literal `SHA-256`.

- [ ] **Step 2: Verify transaction tests fail**

Run: `cargo test archive::transaction --lib`

Expected: FAIL because the transaction engine does not exist.

- [ ] **Step 3: Implement persistent lifecycle records**

Persist operation snapshots with observable states `proposed`, `copying`,
`verified`, `committed`, `failed`, and `abandoned`. Each snapshot records the
operation, actor `desktop-user`, exact source and destination, identity,
confirmation plan/nonce digest, invariant result, outcome, and bounded failure
reason.

- [ ] **Step 4: Implement staged verified commit**

For each plan item:

1. reopen the exact reviewed source with no-follow component traversal;
2. recompute and compare source SHA-256 and byte size;
3. create a unique `.aiks/staging/<operation>.part` with `create_new`;
4. copy from the opened source handle, flush, and sync;
5. independently reopen and hash the staged file;
6. write a non-authoritative pending registration;
7. atomically rename the stage to the exact destination;
8. atomically promote registration to `.aiks/registrations`;
9. persist `committed`;
10. independently verify the source again.

Any failure before completion leaves the source untouched and must not report
a committed result.

- [ ] **Step 5: Implement reconciliation on Vault authorization**

Scan bounded operation records. Remove or abandon incomplete staging output.
For a verified operation with an exposed target, independently hash the target
and promote its matching pending registration; otherwise remove only the
operation-owned target/pending record and mark the operation failed. Never
touch the source during cleanup.
